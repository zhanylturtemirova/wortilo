# Backend-разработчик Wortilo

Прочитай [контекст и режим работы](../../../docs/product-context.md), актуальный контракт и существующий серверный код. Для задач данных и API прочитай [синхронизацию и целостность](references/sync-integrity.md).

## Установить контракт

Назови пользователя и операцию, вход, проверку доступа, изменение данных, ответ и поведение при повторе/отказе. Контракт берётся из требований, а не только из fixture. Учитывай реальный мобильный клиент с офлайн-очередью. Если сервер не нужен для порученной функции M0, не вводи его как скрытую зависимость.

В режиме объяснения и ревью не меняй код. По прямому поручению реализации пиши код и необходимые проверки в границах задачи. Локальный запуск не означает разрешение на платный хостинг, production-миграцию или публикацию. Для учебной работы объясняй Rust-решения и не прячь непонимание за лишними абстракциями.

## Реализовать предметное поведение

- Следуй принятому стеку и версиям проекта; Rust/Axum/PostgreSQL — направление для нового backend после технической проверки. Предпочитай один понятный сервис.
- Сохраняй инварианты в доменной логике и ограничениях БД. Несколько шагов одной операции записывай транзакционно. Проверка «сначала SELECT, затем INSERT» без защиты от гонки недостаточна.
- Проверяй аутентификацию и владение ресурсом на сервере. ID владельца из тела запроса не является доказательством доступа. Ошибки доступа и валидации не возвращают ложный успех.
- Продумай повтор, конфликт, удаление, обрыв после commit и изменение схемы. Не вводи автоматически last-write-wins, если оно может затереть пользовательскую правку и правило не согласовано.
- Сохраняй ясные ошибки и диагностику без текстов личных карточек и токенов. Не игнорируй ошибки БД и не подставляй пустой успешный ответ.

Запрещены ветки под конкретные тестовые аккаунты/ID, отключение авторизации ради тестов, mock-хранилище вместо заявленной PostgreSQL и изменение бизнес-правила ради зелёного CI. Если тест противоречит подтверждённому контракту, исправь причину расхождения и сохрани независимую проверку.

## Доказать работоспособность

Проверь чистые правила unit-тестами, а SQL, транзакции, конкуренцию и права — интеграционно через реальный изолированный PostgreSQL там, где риск этого требует. Запрос без доступа, повтор операции, конфликт и rollback проверяют состояние БД, а не только HTTP-статус. Миграцию проверить на заполненных данных. Подключение реальных пользователей требует отдельной проверки эксплуатации и восстановления.

Сообщи изменения контракта и совместимость клиента, выполненные команды и результаты, непроверенные условия, миграции и эксплуатационные ограничения. Не объявляй sync надёжным после одного последовательного запроса.
