# Правила работы в Wortilo

Этот файл задаёт общие правила для репозитория. Подробные процессы ролей находятся в `.agents/skills/`, поведение продукта — в [docs/product-context.md](docs/product-context.md) и актуальном ТЗ, когда оно добавлено. Не дублируй здесь полный текст skills или спецификации.

## Начало задачи

1. Прочитай контекст продукта и требование текущей задачи. Отличай согласованные требования от предложений и реализованные функции от планов.
2. Проверь фактическую структуру, состояние Git и относящиеся к задаче файлы. Сохраняй чужие незавершённые изменения.
3. Выбери подходящий skill из таблицы ниже. Читай дополнительные references только по затронутой области.
4. Если работа ведётся в подпапке с собственным `AGENTS.md`, прочитай его: локальные правила уточняют работу в этой области. Не переноси их на несвязанные части проекта.

## Учебный режим

Автор учится и остаётся основным разработчиком. При запросе объяснения, плана или ревью давай рекомендации и замечания без правок реализации. Прямой запрос написать тесты, реализовать или исправить конкретную функцию разрешает эту работу в заданных границах; повторное подтверждение не требуется. Объясняй существенные решения так, чтобы автор могла поддерживать результат сама.

Наличие skills или запрос настроить инструкции не поручают создать приложение. Текущая явная инструкция автора имеет приоритет над локальными рекомендациями. Существенное изменение требований, бюджета или состава этапа сначала обозначь; независимую работу продолжай.

## Реализация и проверки

- Делай изменение, необходимое для пользовательского результата. Сохраняй существующие решения и зависимости, пока нет конкретной причины их менять.
- Ожидаемое поведение выводи из требований. Тесты должны обнаруживать правдоподобные дефекты; реализация должна выполнять контракт. Не ослабляй assertions и не добавляй специальные ответы для тестовых данных ради зелёного результата.
- Перед запуском команды найди её в реальной конфигурации: `package.json`, `Cargo.toml`, настройках сборки или документации существующего модуля. Не предполагай наличие pnpm, тестового framework, CI, сервера или preview.
- Запускай проверки, соответствующие изменению. Для документации достаточно проверки ссылок, непротиворечивости и diff; не создавай тесты приложения ради изменения текста.
- Для интерфейса проверяй затронутые состояния и реальные целевые поверхности: клавиатуру, крупный текст, тему, офлайн и отказы, когда они относятся к задаче. Для визуального исправления сравни результат до и после на одинаковом устройстве и состоянии. Недоступную платформу укажи как непроверенную.
- Проверки SQLite, PostgreSQL, синхронизации, разрешений и доставки ОС не подменяй успешными mocks там, где именно эта интеграция является предметом проверки.
- Не объявляй сборку или тесты успешными, если они не запускались. Отделяй дефект продукта от отсутствия инструмента и ошибки окружения.

## Данные и публикация

Используй искусственные воспроизводимые примеры. Не добавляй личные тексты тестировщиков, токены, секреты и сборочные артефакты в публичный репозиторий. Временные скриншоты не коммить автоматически; для запрошенных визуальных доказательств используй обезличенные данные.

Не подключай платную зависимость и не публикуй продукт только потому, что исправляешь локальную задачу. Выполняй явно порученные Git-операции в их объёме. Если создаёшь PR, опиши проблему, результат и фактические проверки; не добавляй несуществующие ссылки и не сливай PR без явного поручения.

## Завершение

Кратко сообщи результат для пользователя, значимые решения, проведённые проверки и оставшиеся ограничения. В ревью указывай место, сценарий и последствия дефекта. Когда структура или команды проекта реально меняются, обновляй относящиеся инструкции; не описывай будущие папки как уже существующие.
